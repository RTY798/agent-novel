# Agent Novel Framework v12：可维护的 AI 长篇小说框架

## 它是什么

这是面向 Claude Code、Codex、Cursor、Windsurf 等 Agent 的中文长篇小说工作流。它不承诺“去除所有 AI 味”，而是用清晰的分工解决更实际的问题：让 AI 不遗忘事实、不偷走作者的判断，并能在百章后仍稳定地写出有变化的章节。

v12 吸收了 `RTY798/agent-novel` 的三型分流、唯一画面、Story Contract、事件冷却、HOT/WARM/COLD、冻结摘要和连贯性门禁；同时将其改造成“事实严格、文风宽容”的系统。

## 继承、改造与删除

| 来源机制 | v12 决定 | 原因 |
|---|---|---|
| A/B/C 三型分流 | 保留 | 情绪、动作、过渡章不应使用同一份检查清单。 |
| 唯一画面 + 写前合同 | 保留并改成章节卡字段 | 让章节的情感/事件承诺可被写后复查。 |
| 事件冷却矩阵 | 保留为预警 | 规避连续同类章节疲劳，但允许作者有理由地破例。 |
| HOT/WARM/COLD | 保留 | 控制上下文负担，按相关性加载信息。 |
| L1 冻结摘要 | 保留为追加式 chapter-log | 已发布事实应可追溯，不应被悄悄改写。 |
| 人名/位置/物品/时间/数字门禁 | 保留并脚本化 | 这些是客观错误，适合自动拦截。 |
| 词语黑名单、破折号数、短段数 | 降级为观察项 | 文字质量由语境决定，不能被形式计数取代。 |
| 每章至少新增一个未解问题 | 删除硬性要求 | 会制造钩子疲劳；收束、休整与代价支付同样是章节价值。 |
| 第 4 章完全免检 | 改为“创作释放章” | 可免风格流程，但不得跳过事实校验。 |
| 刻意保留错别字躲检测 | 删除 | 降低作品质量，也不可持续。 |
| “外部研究”作为确定性结论 | 改为可验证设计假设 | 没有可复核原始来源，不把宣传性数字写成框架事实。 |

## 最小使用流程

### 1. 建立小说

只回答五项：书名、类型与读者、一个核心前提、主角锚点、预计篇幅。先生成最小项目，而不是写一整套没有正文验证的百科全书。

```bash
npm install
npm run init -- "废墟上的炊烟与少年"
```

补全 `project/story-bible.md`，再把开篇时已知的事实写入 `state/story-state.json`。

### 2. 每章先写卡，再写稿

章节卡只有七项：视角与时空、章节类型、目标、阻力、选择、可记录后果、结尾状态。写前先运行：

```bash
npm run check:card -- path/to/chapter-card.md
npm run check:state -- path/to/story-state.json
```

Agent 先给 3—5 个“目标—阻力—选择—后果”场景节拍。作者确认不可逆选择后，才生成首稿。

### 3. 定稿后只追加事实

正文不能反向修改状态。为这一章写一条 `chapter-log.jsonl`，包括发生的事实、资源/位置/关系差分及新增或回收的钩子；随后更新 `story-state.json`。每 5 章把日志与状态比对一次。

## 三型章节

| 类型 | 读者带走什么 | 写前重点 | 写后重点 |
|---|---|---|---|
| A：情绪章 | 一个关系或感受 | 态度如何变化、唯一画面 | 变化是否真的落在行动/语言上。 |
| B：动作章 | 一个具体画面 | 空间、目标、失误、撤退 | 结果是否付出代价，节奏是否有余震。 |
| C：桥接章 | 一条新信息或新的日常秩序 | 世界逻辑、交易理由、角色闲笔 | 信息是否被戏剧化地传递，而非说明书。 |

章节可有次要功能，但只选一个主类型；这样工作流有焦点而不是堆叠规则。

## 章节卡与 Story Contract

每章的三项合同不是 KPI，而是防止“写完才发现本章没有核心”的轻量校准：

1. 变化：某人、关系、信息或资源从什么变成什么？
2. 承诺：读者在这一章应获得什么（画面、紧张、信息、情绪兑现）？
3. 余波：此章结束后的世界与开头相比哪里不同？

注意：余波可以是“一个问题被真正解决”，不必新增悬念。

## 上下文加载规则

- **HOT（每章）**：故事硬规则、当前状态、活跃钩子最多 5 条、当前卡片。
- **WARM（按章）**：上一章结尾、当前视角人物卡、与本章有关的关系/地点资料。
- **COLD（检索）**：旧章节、已归档钩子、世界百科、历史日志。

若 Agent 不确定某个事实，必须检索 COLD；不能用“看起来合理”的补全来代替事实。

## 质量门禁

### 阻断发布的事实错误

- 人物在不可能的时间出现在两地；
- 已损失或消耗的物品无来源地出现；
- 已知信息、感染规则、伤势或人数相互矛盾；
- 章节卡承诺的关键后果没有进入状态日志。

### 必须人工判断的叙事问题

- 场景是否在推进角色、关系、情节、认知或情绪中的至少一项；
- 意外是否来自角色选择，而不是作者临时加设定；
- 角色是否在做“符合局限但并非最优”的人类选择；
- 文字是否有节奏、留白与变化。

### 只记录、不拦截的风格信号

段落长度、破折号、直接情绪词、常见副词、对话比例、感官分布都只提供给编辑判断。禁止“为了骗检测而故意写错字”。

## 关键分歧采用三案，而非让模型选最顺的一案

在死亡、背叛、关系确认、重大转折前，要求 Agent 给出 A/B/C 三个各 2 句的后果方案；作者选择“最符合人物且能制造新后果”的一案。不要选最安全的，也不要为了震惊而选最戏剧化的。

## 创作释放章

每 3—5 章可以选择一章免除所有句式、节奏和风格检查，只保留：章节卡、事实门禁、作者朗读和读者/编辑双视角反馈。这是恢复直觉，不是允许状态失控。

## 项目健康度

| 节点 | 检查 |
|---|---|
| 每章 | 事实校验、章节卡兑现、日志追加。 |
| 每 5 章 | 活跃钩子、资源/伤势、主线推进、角色缺席。 |
| 每 10 章 | 事件分布、角色贡献、关系弧、读者反馈主题。 |
| 每卷 | 读者承诺是否兑现、冲突是否升级、哪些规则应该废弃或放宽。 |

## 发布前清单

- [ ] `npm run check:state` 通过；
- [ ] 章节卡存在，且与定稿一致；
- [ ] 有追加式 chapter log；
- [ ] 所有事实问题已修复或被作者明确标注为有意设定；
- [ ] 作者读过全文并做最终裁决；
- [ ] 没有为规避检测故意损害文本质量。

## 兼容性

Node.js 20+；零运行时依赖。Markdown 模板可在任意编辑器中使用，`SKILL.md` 可放进支持 Agent 指令文件的工具中。
